# AGENTS.md

Guidance for AI coding agents working in this repository. See the [README](README.md) for the full project overview.

## Project

Angular 22 starter (standalone components, zoneless, signals) for apps embedded in a host portal that owns the global chrome: the app only renders its body. It remains a standalone SPA that builds, runs and tests on its own.

Package manager: **pnpm** (version pinned in the `packageManager` field of package.json). Node 24 (`.nvmrc`).

## Commands

| Command                  | Purpose                                                      |
| ------------------------ | ------------------------------------------------------------ |
| `pnpm install`           | Install deps + regenerate the Orval API client (postinstall) |
| `pnpm start`             | Dev server with API proxy                                    |
| `pnpm run test:coverage` | Unit tests with coverage                                     |
| `pnpm run e2e`           | Playwright end-to-end tests                                  |
| `pnpm run lint`          | ESLint (includes Sheriff module-boundary rules)              |
| `pnpm run format:check`  | Prettier check                                               |
| `pnpm run generate:api`  | Regenerate the API client from `openapi/openapi.yaml`        |

Before considering a change done, run the same pipeline as CI: `format:check`, `lint`, `test:coverage`, `build`, `e2e`.

## Architecture

- `src/app/core/` — global infrastructure (i18n, interceptors, logger, 404). `core/api-client/` is **generated by Orval: never edit it**, change `openapi/openapi.yaml` and run `pnpm run generate:api` instead.
- `src/app/features/<feature>/` — one folder per business feature, containing one folder per screen plus `<feature>-routes.ts`. A screen folder is named after its route segment (`list/`, `detail/`, `create/`) and holds everything that serves only that screen: the page, its store if it has one, its form. A feature with a single screen keeps the page at its root (`features/home/home-page.ts`). No `pages/`, `services/` or `forms/` folders: grouping is by domain, not by technical type.
- **`<feature>-routes.ts` is the feature's public API** — every feature has one, whatever its number of screens, and it owns the feature's paths, titles and `provideTranslocoScope`. `app-routes.ts` imports that file and nothing else from the feature: it never reaches for a page directly. A feature is then relocatable (to another app, to another MFE) by moving its folder and changing one import.
- `src/app/shared/` — reusable presentation/test helpers, imports neither `core` nor `features`.
- Module boundaries are enforced at lint time by Sheriff ([sheriff.config.ts](sheriff.config.ts)): `features` → `core`/`shared`; `core` → `shared`; features never import each other. Modules are barrel-less: no `index.ts`, import files directly; private files go in an `internal/` subdirectory.
- Import aliases: `@core/*`, `@features/*`, `@shared/*`, `@environments/*`.

## Adding a page to a feature

1. Create `<feature>/<screen>/` where `<screen>` is the route segment, with `<entity>-<screen>-page.ts` (+ `.html`, `.spec.ts`), class `<Entity><Screen>Page`, selector `app-<entity>-<screen>-page`. **The folder carries the short name, the files carry the full one** — `users/list/user-list-page.ts`, never `users/user-list-page/user-list-page.ts`.
2. Name the screen after what it is, not after the CRUD operation, and stick to `list`, `detail`, `create`, `edit`, `form`. One screen handling both creation and update is `form/<entity>-form-page.ts`, with the mode derived from the presence of the route parameter.
3. If the page has any I/O, inject the generated client (`core/api-client/<feature>/<feature>.service.ts`) into the page or its store and build the `rxResource` there — see "State and data access" below.
4. Wire the page into `<feature>-routes.ts`, with a `pageTitle.<key>` title.
5. Add its translations under the feature's i18n scope (`public/i18n/<feature>/<lang>.json`), keyed by screen (`<feature>.<screen>.*`) — see `users.list.*`, `users.create.*`, `users.detail.*`.
6. A form used by a single page is colocated with it (`create/user-create-form.ts`), not in a feature-wide folder.

## State and data access

- **A page never injects the API client.** Any I/O lives in a `<screen>-store.ts` colocated with the screen, and the page interacts with nothing but that store. The store is a **private** dependency (`#store`) and the page re-exposes what its template consumes (`protected readonly user = this.#store.user`), so templates never carry a `store.` prefix: where the data comes from is not the view's business. This is a layering rule, not a size threshold: no judgment call about when a page has grown enough. A screen with local state but no I/O can still keep it in the component; a screen with neither (`home-page.ts`) has no store at all.
- **A store is provided by its route** (`providers: [UserListStore]` in `<feature>-routes.ts`), never `providedIn: 'root'`: screen state must be created and destroyed with the screen. Specs must mirror that wiring, like they already do for `provideTranslocoScope`.
- **The store owns the route parameters it depends on**, read from `ActivatedRoute` (see `user-detail-store.ts`) — it is scoped to that route, so it is the natural owner of "what am I looking at". A page therefore has no route input to forward.
- **Navigation stays in the page.** A store returns a result (`UserCreateStore.save()` returns the created user or `undefined`); the page decides where to go next. A store that injects `Router` knows too much.
- **HTTP goes through the generated client**, injected by the store. Add a hand-written `<feature>-repository.ts` at the feature root only when it earns its place — aggregating several calls into one business operation, mapping DTOs to a view model shared by several pages, or absorbing an API quirk. Never as a pass-through.
- **Shared code moves up to the nearest common ancestor**: the feature root for two screens of one feature, `shared/` beyond. Two sibling screens never import each other (Sheriff cannot catch this — they belong to the same module).
- **Share the rule, not the shape.** Factor something out only when a change to one screen must change the other; validators and schema fragments (`apply()`) are worth sharing, form models tied to different endpoints are not (same reasoning as one DTO per endpoint).

## Conventions

- Everything in the repo is written in **English** (code, comments, docs, commit messages).
- Commits follow [Conventional Commits](https://www.conventionalcommits.org), enforced by commitlint. lint-staged formats and lints staged files on commit.
- OnPush is Angular 22's default change detection: do **not** add `ChangeDetectionStrategy.OnPush` to components.
- `inject()` + `#` private fields; signals and `rxResource` for data/error/loading state; no NgRx.
- Never suffix a class with `-service`: name it after the role it plays (`-store` for state, `-repository` for adapted data access, `-http-client`). Generated code is the exception — it keeps its generator's naming and is never edited.
- Forms use Signal Forms (`@angular/forms/signals`): model factory + `schema()`, colocated with the page that uses them. Compose schemas with `apply()` rather than parameterizing one schema for two screens.
- `verbatimModuleSyntax` is enabled: type-only imports must use `import type { X }` or `import { type X }`.
- `console` is forbidden (ESLint) outside `core/logger` and `main.ts` — inject `LoggerService`.
- File names separate words with dashes, never dots: `logger-service.ts`, `users-routes.ts` and `app-config.ts`, not `logger.service.ts`, `users.routes.ts` or `app.config.ts` (this departs from what `ng new` generates). Classes are named after their role (`home-page.ts`, `user-list-store.ts`, `not-found-page.ts`), never after their Angular type. `core/api-client/` is the exception: it is generated by Orval and keeps its own naming.

## i18n (Transloco)

- The global `public/i18n/<lang>.json` files only hold keys needed synchronously before any scope loads: `pageTitle.*` (used by the title strategy on navigation) and the 404 page. They are preloaded by an app initializer — keep them minimal.
- Each feature has a lazy scope in `public/i18n/<feature>/<lang>.json`, declared with `provideTranslocoScope('<feature>')` in the feature's routes. Keys are prefixed with the scope (`users.list.title`).
- Every key must exist in both `en` and `fr`.

## Testing

- Component tests use Angular Testing Library (`render`, `screen`, `userEvent`): query by role or label, not by CSS selectors. Stores, interceptors and form schemas use plain `TestBed` (a store is tested without rendering its page — see `user-list-store.spec.ts`, where `TestBed.tick()` flushes the effect that fires the request). jest-dom matchers are set up in `src/test-setup.ts`.
- Zoneless + `rxResource` pitfalls: rendering (which runs change detection) must happen **before** flushing the `HttpTestingController`, and never `await fixture.whenStable()` before the flush (it hangs). After a flush, use `findBy*` queries (they re-run change detection).
- Form submission and `rxResource` reloads reach HTTP through microtasks: wrap `expectOne` in `await vi.waitFor(...)`.
- Coverage is at 100% and must stay there; the CI thresholds (85/80/70/85) are intentionally lower so downstream users of the starter are not blocked — do not raise them.
- `data-testid` attributes in templates are used by the Playwright e2e page objects — keep them even where unit tests query by role.

## Generator

New applications are scaffolded from this starter by [starter-generator](https://github.com/JoanRoucoux/starter-generator), a generic engine: everything starter-specific lives **here**, in [generator.config.json](generator.config.json) (files removed from generated apps, renames, install commands — full spec in the generator's README) and `.generator/templates/` (scaffold files rendered with `{{token}}` content placeholders and `__feature__` path placeholders).

Keep them in sync with the starter:

- `.generator/templates/src/app/shared/testing/transloco-testing.ts` mirrors [src/app/shared/testing/transloco-testing.ts](src/app/shared/testing/transloco-testing.ts) with the demo scopes swapped for `{{feature}}` — when one changes, change the other.
- The scaffold templates (feature page, routes, i18n files, e2e spec) follow the conventions of this file — when a convention changes, re-check the templates.
- Template-only content (demo features, community files, release tooling) must be listed in the manifest's `remove`; new root-level files that should not ship in generated apps must be added there.
- Templates contain tokens and are not valid syntax: `.generator/templates/` stays excluded in [.prettierignore](.prettierignore) and the ESLint `globalIgnores`.
- The `generate` job in [ci.yml](.github/workflows/ci.yml) generates an app from the working tree and runs its quality gates — it fails when the manifest or templates drift.

## Gotchas

- `typescript` is pinned to `~6.0.2`: TypeScript 7 breaks `typescript-eslint` (via `ts-api-utils`). Do not bump until typescript-eslint supports TS 7.
- `pnpm-workspace.yaml` `allowBuilds` is required for native postinstall scripts (esbuild, lmdb, ...) — do not remove it.
- GitHub Actions in `.github/workflows/ci.yml` are pinned by commit SHA (Dependabot keeps them updated) — when adding one, pin it the same way.
- Nothing is committed or pushed without an explicit request from the maintainer.
